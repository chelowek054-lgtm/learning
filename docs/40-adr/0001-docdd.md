# ADR-0001 — Документация — источник правды; изменения идут по DocDD

| | |
|---|---|
| **Статус** | `accepted` |
| **Дата** | 2026-09-30 |
| **Затрагивает** | всё |

## Контекст

Документация с самого начала объявлялась источником правды, но держалась только на дисциплине. К 2026-09-30 она разошлась с кодом и сама с собой:

- корневой README показывал Фазу 2 «в работе, 9/21», а ROADMAP — «закрыта, 21/21»;
- план Ф1 отмечал сделанными учёт токенов и кэш генерации, которых в коде нет;
- функциональный план держал устаревший роадмап.

Требований с критериями приёмки не было, и задачам плана не на что было ссылаться.

## Решение

Проект ведётся по **Documentation-Driven Development**:

1. Цепочка трассировки: `00-product → FR/NFR → SPEC → ADR → задача плана → код → проверка`. Каждое звено ссылается на предыдущее.
2. Поведение меняется в порядке «требование → спека → план → код», устройство — «ADR → архитектура → спека → план → код».
3. У спеки обязательны критерии приёмки и раздел «Код». Каждое расхождение с кодом записывается строкой со ссылкой на задачу.
4. `ROADMAP.md` только сводит статусы и ничего не определяет сам.
5. Сверка документации с кодом входит в DoD каждой фазы (NFR-19).

## Рассмотренные варианты

| Вариант | За | Против |
|---|---|---|
| Оставить как есть: архитектура + чеклисты фаз | Меньше документов | Расхождения копятся; «сделано» без проверяемого критерия |
| Спеки в коде (docstrings, OpenAPI) | Не расходятся с кодом | Не описывают будущее; негде жить продуктовым решениям |
| DocDD с трассировкой | Проверяемые критерии; видно, откуда взялась каждая задача | Больше документов; нужна дисциплина обновления |

## Последствия

Документации становится больше. Это компенсируется тем, что спеки заменили разрозненные описания в ROADMAP, HANDOFF и планах. Проверка ссылок и инвариантов уходит в CI (P3-CI-03). Правила — в [docs/README.md](../README.md#правила-docdd).
