# Развёртывание модулей в одном процессе, REST для графа, вектора в Postgres, владелец данных пользователя, исполнение на устройстве

Пять связанных решений, нужных до начала контракта модуля:
1. Модули разворачиваются в одном процессе, границы — как у сервисов (свои таблицы, доступ к чужим данным только через шлюз); вынос в отдельный сервис — когда появится нагрузка или отдельная команда. Теряем: независимое масштабирование до выноса.
2. API модуля графов — REST с выбором полей, не GraphQL; второй стиль API не окупается, пока клиент не упирается в размер ответов (уже решено лёгким списком узлов).
3. Векторный поиск близких областей — расширение векторов в той же базе Postgres, не отдельное хранилище, до упора в объём.
4. Освоенность и результаты мини-приложений хранятся в модуле данных пользователя (шестой модуль рядом с пятью), а не в личном графе: граф хранит структуру, не результаты.
5. Мини-приложения исполняются на устройстве, в ограниченной среде; свои — через манифест сейчас, песочница для чужих и сервер для исполнения чужого кода — позже.
Чего не делаем: не дробим на сетевые сервисы заранее; не пускаем стороннее мини-приложение к данным без разрешений и журнала доступа.
Что мешает: сегодняшние предметные модули подключены по старому контракту реестра — перенос на шлюз предстоит отдельной работой перехода к платформе.
