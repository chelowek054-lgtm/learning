# Контракт модуля: манифест, жизненный цикл, версии

Зачем: чтобы ядро и модули развивались независимо, граница должна быть записана. Сегодня у серверных модулей свой небольшой контракт (маршруты, рубрики, типы задач, стартовый контент, вид админки), у клиентских — манифест типов активностей; они не связаны и не рассчитаны на сторонних авторов.

Договорённость: модуль описывается одним манифестом — идентификатор, название, версия, версия контракта ядра, список возможностей, которые он даёт, список возможностей и данных, которые просит. Ядро проверяет манифест при подключении и отказывает с понятной причиной при несовместимой версии, запрещённом запросе или занятом идентификаторе. У модуля есть жизненный цикл: установка, включение, отключение, обновление, удаление; отключение не ломает остальные модули и не удаляет данные без явной команды. Зависимости между модулями объявляются явно и не образуют цикла. Контракт ядра версионируется: старые модули работают на прежней версии до обновления.

Не делаем: не даём модулю доступ к внутренним таблицам ядра напрямую — только через объявленные интерфейсы; не делаем контракт «на вырост».

Что мешает: не решено, где исполняется модуль; клиентский и серверный манифесты устроены по-разному.
