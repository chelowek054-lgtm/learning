# Справочник проекта

Сгенерировано приложением, не править: источник — справки (S-…) и подтверждённая карта кода (docs/13-reference.md).

## Модули проекта
Что уже написано. Прежде чем заводить новое — посмотри, нет ли такого.

### «Мои данные»: доступ, выгрузка, удаление — Реестр типов данных человека с разрешениями модулям, журналом доступа, выгрузкой, удалением по типу, по сроку хранения и удалением аккаунта.
- `learningBack/core/userdata.py` — Данные учащегося принадлежат платформе, а не модулям: модуль просит тип данных через этот интерфейс, ядро проверяет объявление в манифесте и разрешение человека и пишет в журнал. Отсюда же выгрузка, удаление по типу, удаление по сроку хранения и удаление аккаунта.
- `learningBack/api/routers/userdata.py` — Экран «Мои данные»: какие типы данных хранятся, разрешения модулям по типу и режиму, журнал обращений, выгрузка и удаление всех данных или аккаунта целиком. Отдельно — запуск удаления по сроку хранения.
### Аккаунт и вход — Регистрация, вход, восстановление пароля по коду, JWT-сессия и состояние аутентификации на клиенте — всё, что отвечает на вопрос «кто сейчас работает».
- `learningFront/src/entities/session/index.ts` — Единственная точка, откуда остальной код узнаёт состояние аутентификации и предмет изучения: провайдер и хук сессии плюс целевые ступени владения и утилиты предмета (slug, подпись цели, чтение из профиля).
- `learningFront/src/shared/api/token.ts` — JWT хранится в expo-secure-store.
- `learningBack/core/security.py` — Хеширование паролей (argon2 через pwdlib) и работа с JWT-токенами собственной аутентификации, включая версионирование сессий. Отдельно реализует генерацию и HMAC-хеширование короткого числового кода восстановления пароля.
- `learningBack/api/routers/auth.py` — Эндпоинты собственной аутентификации: регистрация, вход, восстановление пароля по временному числовому коду (с лимитом частоты запросов) и профиль пользователя. Смена профиля с выбранным предметом запускает идемпотентное провижининг стартового контента через модули.
- `learningBack/core/ratelimit.py` — Ограничитель частоты запросов на основе скользящего окна в памяти процесса — используется для защиты запроса кода восстановления пароля от перебора. Хватает одного экземпляра API: при нескольких воркерах счётчики не общие.
- `learningFront/src/shared/api/auth-api.ts` — Регистрация, вход, выход (очистка токена), восстановление пароля в два шага (запрос кода / подтверждение с одинаковым ответом и для незарегистрированного email — иначе форма позволяла бы перебирать адреса), чтение и обновление профиля. При успешном входе/регистрации сохраняет JWT локально.
### Выбор способа изучения (клиент) — Что можно выбрать для шага изучения и что выбрано сейчас, плюс запросы к серверу за этим выбором.
- `learningFront/src/features/study-method/index.ts` — Наружу виден только компонент выбора способа изучения шага remember; логика, что можно выбрать и что выбрано сейчас, остаётся внутри фичи.
- `learningFront/src/features/study-method/model/options.ts` — Чистая логика без сети и UI: какие способы шага предложены (только входящие в курс), какой из них действует сейчас и можно ли выбирать вовсе — выбор доступен только тогда, когда способов больше одного. Без явного выбора человека действует первый предложенный способ — то же правило, что и на сервере.
- `learningFront/src/shared/api/methods-api.ts` — Запросы к выбору способа для шага изучения: какие способы предложены и что выбрано сейчас. Смена способа пересобирает курс на сервере, но освоенность не трогает — способ меняется, цель остаётся.
### Граф знаний (клиент) — Экран карты знаний и курирование канона: чтение эффективного графа, теория и задание узла, правка summary, построение по теме.
- `learningFront/src/features/concept-study/index.ts` — Два рендерера узла графа знаний: теория (ConceptStudyActivity) и проверка понимания заданием (ConceptQuestionActivity).
- `learningFront/src/shared/api/graph-api.ts` — Клиент графа знаний: чтение эффективного графа и узла, канон-курирование, адаптивный плейсмент, курс и его шаги, рост ветки; с T-0015/T-0016 — построение личных узлов и вопросов на вспоминание из материала пользователя.
### Граф знаний (ядро) — Канонический граф понятий и персональный слой поверх него (copy-on-write): теория узла, задания, байесовская освоенность, адаптивный плейсмент, курс как траектория и промоция личных узлов в канон.
- `learningBack/modules/knowledge/models.py` — ORM-таблицы слоя знаний: канонический граф (Concept, ConceptEdge), персональный слой поверх него по COW (UserConcept, UserEdge), кэш заданий (Assessment) и сохранённый курс (Course). Таблицы данные модуля, а не логика ядра.
- `learningBack/modules/knowledge/assessment.py` — Строит задания (test/practice/probe) строго по содержимому content узла — промпт собирается из разделов, примеров и контрпримеров, а узлы без достаточной теории отсекаются до вызова LLM. Ступень Блума задаёт, что спрашивать, kind — форму вопроса.
- `learningBack/modules/knowledge/mastery.py` — Байесовская оценка освоенности на бета-распределении с приором от освоенности предпосылок (минимум, не среднее) и правилом статуса locked/frontier/learning/known; освоенность персональна и живёт в user_concept.mastery.
- `learningBack/modules/knowledge/ai.py` — Доменная JSON-схема графа узлов с теорией и промпты для построения черновика темы и дорастания ветки от узла через core.ai_gateway.structured(). Детерминированные заглушки на случай отсутствия ключа живут здесь же, а не в core, потому что предметное знание — не дело ядра.
- `learningBack/modules/knowledge/assessment_store.py` — Кэширует результат генерации заданий в таблице assessment по ключу (concept_id, concept_version, bloom, kind): правка теории растит версию и автоматически обесценивает старые задания, строки прежних версий удаляются при записи новой.
- `learningBack/modules/knowledge/placement.py` — Подбирает следующий зонд на границе знаний пользователя (предпосылки освоены, неопределённость ещё заметна) с приоритетом по centrality узла, записывает ответ в модель освоенности и строит карту освоенности домена.
### Граф областей — Реестр базовых областей, связи «нужно знать до» и вычисляемый уровень примитивности, с API для чтения и курирования.
- `learningBack/modules/knowledge/domains.py` — Области становятся данными: реестр по устойчивому ключу с алиасами, связи «нужно знать до» без циклов, нижняя опора без предпосылок. Уровень примитивности не назначается руками — это вычисляемая глубина области в графе.
- `learningBack/modules/knowledge/domains_api.py` — Эндпоинты графа областей: читать может любой вошедший, заводить область и связи — куратор, так как канон общий.
### Данные задания Task 1 (клиент) — Разбор и отрисовка числовых данных графика или таблицы задания Task 1 — читается офлайн, без картинки с сервера.
- `learningFront/src/features/ielts-writing/lib/task-data.ts` — Данные графика или таблицы задания Task 1 приходят как числа в payload.data, а не картинкой — поэтому их можно отрисовать и прочитать офлайн. Модуль проверяет форму пришедших данных, не доверяя им, готовит строки для столбчатой диаграммы и считает нехватку слов до минимума эссе.
- `learningFront/src/features/ielts-writing/ui/task-data-view.tsx` — Отрисовывает данные задания Task 1 столбчатой диаграммой и теми же цифрами текстом рядом — цифры нужны всегда: по ним пишут описание и по ним же проверяют точность написанного.
### Диалог постановки цели — Уточняющие вопросы, пересказ и подтверждение цели перед тем, как граф начнёт строиться.
- `learningBack/modules/knowledge/goal_intake.py` — Голая строка «название предмета» не даёт ни уточнить, ни проверить, что система поняла цель человека. Модуль ведёт диалог: свободный ввод → 2–4 уточняющих вопроса (не обязательных) → пересказ «область, цель, уровень, пожелания» → явное подтверждение; пока цель не подтверждена, граф не строится. Хранится только итог пересказа, а не вся переписка.
### Диалог постановки цели (клиент) — Компонент и логика диалога постановки цели: уточняющие вопросы, пересказ, подтверждение; публичная точка входа фичи.
- `learningFront/src/features/goal-intake/index.ts` — Наружу видны только компонент диалога постановки цели и функция сборки предмета профиля из подтверждённого пересказа; модель диалога и сам компонент остаются внутренними деталями фичи.
- `learningFront/src/features/goal-intake/model/dialog.ts` — Чистая логика диалога постановки цели без сети и UI: сбор ответов на уточняющие вопросы (пустое поле — пропуск, а не пустой ответ), проверка готовности к пересказу и подтверждению, правка пересказа человеком, строка пересказа, сборка предмета профиля и решение о показе выбора между полным и интуитивным путём с человекочитаемым объёмом пути.
### Диспетчер активностей и реестр модулей (клиент) — По типу активности находит и рендерит нужный компонент среди подключённых предметных модулей — ядро клиента не знает их имён; собирает манифесты модулей воедино.
- `learningFront/src/shared/engine/index.ts` — Публичный барьер доменно-независимого ядра (инвариант №3 — здесь нет строк, специфичных для предметных областей): типы активности/оценки/ответа, контракт модульной системы и реестр модулей, планировщик интервальных повторений FSRS, и порты LocalStore/SyncClient/JobQueue, которые реализуют адаптеры вне ядра.
- `learningFront/src/entities/module/index.ts` — Собирает воедино чистые метаданные трёх подключаемых предметных модулей (languages/ml/knowledge) — только id, заголовок и список типов активностей, без рендереров. Сборка реестра с рендерерами по этим же метаданным живёт в widgets/module-registry, куда entities по правилам FSD импортировать не может.
- `learningFront/src/shared/engine/module/manifest.ts` — Описание типа активности (ActivityTypeDef) с человекочитаемым названием и подсказкой — раньше их не было, и экраны печатали технический слуг типа (concept_recall) вместо названия; opaque-рендерер активности, чтобы ядро не зависело от React; офлайн-грейдер как мгновенный черновой сигнал без LLM; описание импортёра и конфиг планировщика. ModuleManifest собирает всё это в один пакет на предметную область.
- `learningFront/src/shared/engine/module/registry.ts` — Табличный lookup типов Activity по модулям (инвариант №3 — ни одного `if module === ...`): регистрация манифеста с запретом повторной регистрации и коллизий типов между модулями, поиск рендерера/офлайн-грейдера/названия типа для человека по строке type. Незнакомый тип отдаёт сам слуг вместо пустоты — это заметно на экране.
- `learningFront/src/shared/engine/types/activity.ts` — Центральная доменно-независимая абстракция ядра: владелец-модуль и type задают диспетчеризацию рендерера, а структуру payload валидирует сам модуль — ядро её не интерпретирует.
- `learningFront/src/shared/engine/types/response.ts` — Единый event log ответов — единственное, что читают FSRS и адаптивный план (инвариант №4): ответ пользователя, результат скоринга или null пока job pending, локальное время (офлайн-first) и признак синхронизации.
- `learningFront/src/shared/lib/module-registry-context.tsx` — React-контекст реестра модулей — позволяет pages/widgets читать реестр, не импортируя app-слой напрямую (правило FSD: импорты только вниз).
### Ежедневный цикл (клиент) — Экран «Сегодня» решает единственное следующее действие (шаг курса, повторение или определение уровня) и очередь повторения просроченных карточек.
### Жизненный цикл и манифест модуля — Контракт манифеста и администраторские действия над подключённым модулем: включить, согласиться на расширение, отключить, удалить данные.
- `learningBack/core/manifest.py` — Модуль описывает себя манифестом: id, версия, версия контракта ядра, что даёт и просит, зависимости, разрешённая сеть. Ядро проверяет манифест при подключении набора модулей — неизвестный запрос, несовместимый контракт, цикл зависимостей — и отказывает с понятной причиной.
- `learningBack/api/routers/modules_admin.py` — Жизненный цикл подключённого модуля для администратора: список, включение, согласие на расширенные разрешения, отключение, необратимое удаление данных.
### Заслон перед построением карты — Блокирует построение графа, пока цель по области явно не подтверждена.
- `learningFront/src/features/graph-editor/ui/goal-gate.tsx` — Пока цель по области не подтверждена явно, построение карты знаний недоступно. Для целей, уже заданных прямой формой или до появления диалога постановки цели, подтверждение — одна кнопка по уже введённым области и уровню.
### Изоляция исполнения модуля — Единственный путь модуля к данным и сети с лимитами по времени, частоте и сбоям.
### Инструменты DocDD — Скрипты, которыми проверяется само ведение процесса: ссылки в документации, прогон проверок верификации, матрица трассируемости требований и живые прогоны против настоящего провайдера модели.
### Каркас backend — Сборка FastAPI-приложения, настройки, подключение к БД, общие зависимости запроса, ORM-модели ядра и реестр подключаемых модулей — то, чем пользуются все остальные части backend.
- `learningBack/core/models.py` — ORM-модели 10 таблиц ядра Praxis: пользователи, event log ответов (`Response`), активности, SRS-карточки, отложенные AI-задачи (`Job`), материалы, версионируемые рубрики-оценщики и учёт расхода токенов LLM с их кэшем. Разделение на предметные модули идёт колонками (`module`, `connectivity`), а не отдельными схемами.
- `learningBack/core/deps.py` — FastAPI-зависимости: сессия БД на запрос и определение текущего пользователя по Bearer JWT. Отдельно проверяет `token_version`, чтобы токены, выданные до смены пароля, переставали действовать, и добавляет отдельную зависимость для проверки прав суперпользователя.
- `learningBack/core/modules.py` — Реестр подключаемых предметных backend-модулей (SPEC-01, ADR-0019): ядро обращается к ним только через контракт `BackendModule`, не зная их имён и импортов напрямую — список берётся из конфига `INSTALLED_MODULES`. Через него же синхронизируются рубрики-оценщики модулей с БД и определяется, какой модуль обрабатывает конкретный тип задачи или область практики.
- `learningBack/core/config.py` — Единая точка настроек приложения из переменных окружения (pydantic-settings), читает `.env` из корня суперпроекта, а не из своей копии. Собирает `DATABASE_URL` из отдельных POSTGRES_*-полей, если он не задан явно, и запрещает dev-секреты (JWT, пароль БД) при запуске в staging/production.
- `learningBack/tests/conftest.py` — Общие pytest-фикстуры: отдельная тестовая БД с пересозданной схемой на сессию, тест в откатываемой транзакции, перехват записи учёта токенов вместо похода в рабочую БД, принудительное отсутствие LLM-ключа в тестах и TestClient с подменой текущего пользователя.
- `learningBack/core/db.py` — Создаёt SQLAlchemy engine и фабрику сессий на базе `settings.database_url`, а также базовый класс `Base` для всех ORM-моделей ядра и модулей. Движок ленивый: соединение не устанавливается при импорте, поэтому /health не зависит от доступности БД.
- `learningBack/core/schemas.py` — Pydantic-схемы входов и выходов API ядра. Схемы синхронизации используют camelCase-алиасы, чтобы совпадать с типами TS-клиента.
- `learningBack/api/app.py` — Собирает FastAPI-приложение Praxis: подключает CORS и middleware учёта пользователя, регистрирует роутеры ядра и роутеры подключённых предметных модулей, монтирует админку. При старте (lifespan) синхронизирует рубрики модулей с БД, но не падает, если БД недоступна — /health должен отвечать всегда.
### Контракт способа изучения — Общий способ, которым модуль объявляет способ изучения шага курса и отдаёт его через API выбора и смены.
- `learningBack/core/methods.py` — Контракт способа изучения (карточки, письмо с оценкой, мини-игра): на входе узлы к проработке, на выходе активности; результат способ сообщает только как свидетельство (core.evidence). Модуль объявляет способы и шаг курса, который они исполняют; выбор человека хранится в его профиле.
- `learningBack/api/routers/methods.py` — Эндпоинты для выбора способа изучения на шаг курса и приёма свидетельств об освоении от любого способа. Освоенность, ошибки и карточки при смене способа не трогаются.
### Локальный движок и синхронизация — Офлайн-first ядро клиента: локальное хранилище активностей/ответов/карточек, планировщик FSRS и двухфазная push/pull синхронизация с backend-эндпоинтом sync.
- `learningBack/core/srs.py` — Хелперы SRS ядра: начальное состояние карточки в формате ts-fsrs и превращение ошибок из оценки (Grade) в заготовки карточек error-log, а также их вставка в БД — связывает движок оценки с движком интервальных повторений независимо от модуля.
- `learningFront/src/shared/api/current-user.ts` — Достаёт поле sub из JWT без проверки подписи (её делает сервер при каждом запросе) — нужен только чтобы привязать состояние синхронизации к аккаунту, потому что локальная база не очищается при смене пользователя.
- `learningFront/src/shared/api/db/sqlite-local-store.web.ts` — Metro подхватывает этот файл вместо нативного на платформе web, потому что expo-sqlite там требует wa-sqlite.wasm и COEP/OPFS. In-memory реализация того же порта с тем же публичным API — данные не персистентны, но веб-превью работает.
- `learningBack/api/routers/sync.py` — Двухфазная синхронизация клиента: `push` принимает локальные изменения активностей/ответов/SRS-карточек/задач (id генерирует клиент, чужие id отклоняются) и сразу обрабатывает отложенные задачи; `pull` отдаёт серверные изменения новее курсора `since`. Карточки разрешаются по LWW через `updated_at`.
- `learningFront/src/shared/api/auto-sync.ts` — Чистый контроллер (createAutoSync) запускает sync на переходе offline→online или при возврате приложения из фона, без гонок — пока sync идёт, новые триггеры схлопываются в один повторный запуск после него, а ошибки не всплывают. startAutoSync навешивает это на реальные подписки expo-network и AppState и возвращает функцию отписки.
- `learningFront/src/shared/api/db/sqlite-local-store.ts` — Нативная реализация порта LocalStore: схема создаётся идемпотентно при старте (CREATE TABLE IF NOT EXISTS плюс ручное добавление колонок у старых установок), таблицы activity/response/srs_card/job/sync_state хранят офлайн event log, SRS-карточки, очередь задач на скоринг и курсор синхронизации.
- `learningFront/src/shared/api/grading.ts` — Общий поток: записывает ответ в event log (response) и ставит задачу на скоринг (job) нужного типа — работает офлайн, задача резолвится при следующей синхронизации.
- `learningFront/src/shared/api/job-queue.ts` — Реализация порта JobQueue поверх LocalStore: добавление идемпотентно по id, задачи резолвятся с результатом либо помечаются failed.
- `learningFront/src/shared/api/local-store.ts` — Одно соединение SQLite на всё приложение, общее для всех фич, чтобы не плодить параллельные подключения к одной базе.
- `learningFront/src/shared/api/sync-client.ts` — Реализация порта SyncClient поверх HTTP: push отправляет накопленные локальные изменения, pull запрашивает серверные начиная с курсора (или всё, если курсора нет); camelCase полей совпадает с алиасами backend.
- `learningFront/src/shared/api/sync-service.ts` — Push локальных изменений (активности с момента прошлого push минус запас на расхождение часов, неотправленные ответы, pending-задачи, неотправленные SRS-карточки), затем pull с сервера и применение — карточки вставляются insert-only, чтобы не затереть локальный прогресс FSRS, а прогресс карточек уходит наверх и побеждает по updatedAt на сервере (LWW, FR-SYNC-08). Состояние {userId, cursor, pushedAt} сохраняется последним и привязано к аккаунту (T-0048), чтобы обрыв не терял курсор, а смена пользователя не путала историю.
- `learningFront/src/shared/engine/ports/jobs.ts` — Контракт очереди отложенных AI-задач — мост офлайн→онлайн: постановка задачи идемпотентна по id, чтение ожидающих, пометка успеха с результатом или неуспеха. Реализацию даёт адаптер вне ядра.

- `learningFront/src/shared/engine/ports/sync.ts` — Контракт двухфазной синхронизации push/pull между клиентом и backend: что отправляется локально изменённое и что приходит с сервера — включая курсор для следующего pull и userId, без которого клиент не отличит локальный курсор от курсора другого аккаунта.
- `learningFront/src/shared/engine/scheduler/scheduler.ts` — Тонкая обёртка над ts-fsrs, работает офлайн на клиенте: создание новой карточки, пересчёт состояния и срока следующего показа после отзыва пользователя (снова/трудно/хорошо/легко), отбор карточек с наступившим сроком.

Отправка офлайн-безопасна: без сети свидетельство ждёт в очереди на устройстве, привязанной к владельцу, и уходит при следующей синхронизации; отказ сервера по существу очередь не трогает.
### Слияние карточки повторения (клиент) — Правило выбора более свежей версии карточки повторения при синхронизации с нескольких устройств.
- `learningFront/src/shared/engine/scheduler/card-merge.ts` — Правило слияния — то же, что на сервере (core/srs.py: review_key): побеждает более позднее ревью, а не более поздняя запись, при равном времени решают число повторов и затем срывов. Карточка без ревью или с мусором вместо даты считается старше всех, а время без явной зоны читается как UTC.
### Техники запоминания — Две техники по общему контракту способа изучения: интервальное повторение и вспоминание по первым буквам.
### Техники запоминания (клиент) — Клиентская часть техники «вспомнить по первым буквам»: метаданные модуля для реестра, самооценка вспоминания и публичный API фичи с рендерером активности.
- `learningFront/src/features/mnemonic-recall/model/rating.ts` — Самооценка вспоминания по технике «первые буквы» переводится в результат 0..1 той же шкалой ступеней (не вспомнил/с трудом/хорошо/легко), что и оценка карточки интервального повторения — освоенность в графе знаний общая независимо от техники.
- `learningFront/src/entities/module/mnemonic.ts` — Клиентские метаданные второй техники запоминания — тот же набор полей, что у остальных предметных модулей (languages/ml/knowledge): только id, заголовок и единственный тип активности concept_mnemonic, офлайн, без схемы payload. Чистые данные без рендерера — рендерер (MnemonicActivity) подключается отдельно в widgets/module-registry, куда entities импортировать нельзя.
- `learningFront/src/features/mnemonic-recall/index.ts` — Наружу виден только рендерер активности concept_mnemonic.
### Трек программирования/ML (ядро модуля) — Типы активностей и рубрики модуля ML: проверка понимания концепции и ревью кода, определение ML-предмета и минимальный генератор активностей из материала.
- `learningBack/modules/ml/rubrics.py` — Рубрики-оценщики модуля ML: проверка понимания концепции (concept_check) и статическое ревью решения задачи на код (ml_code_review v2 — v1 занята неактуальной заглушкой Фазы 0, рубрики не перезаписываются).
### Устный ответ — Загрузка записи устного ответа, расшифровка и метрики темпа/пауз для оценки.
- `learningBack/modules/languages/speaking_api.py` — Принимает запись устного ответа с устройства и сразу ставит job `transcribe` в очередь; файл виден только владельцу.
### Устный ответ (клиент) — Запись устного ответа офлайн с лимитом времени, очередь на отправку записи и рендерер активности.
- `learningFront/src/shared/api/voice-outbox.ts` — Ответ записан без сети — файл ждёт на устройстве и уходит при синхронизации; после успешной загрузки локальный файл удаляется сразу, поскольку голос — биометрия, а на сервере дальше живёт только расшифровка. Запись, которую не отправить из-за сети, остаётся в очереди вместе с файлом; отказ сервера по существу (пустая или слишком большая запись) снимает её с очереди.
- `learningFront/src/features/speaking/index.ts` — Наружу виден только рендерер активности speaking_response; модель разбора задания и правила записи остаются внутри фичи.
- `learningFront/src/features/speaking/model/speaking-model.ts` — Чистый разбор задания устного ответа (тема, лимит записи) без звука и сети: лимит по умолчанию подставляется, если задание не указало свой. Отдельно — причина, по которой слишком короткую запись нельзя отправить: в ней заведомо нет содержательного ответа.
### Шлюз к языковой модели — Единая точка вызова LLM-провайдера с кэшем детерминированных ответов и учётом расхода токенов — графовые и языковые модули используют её, не зная деталей провайдера.
- `learningBack/core/usage.py` — Учёт расхода токенов LLM: ASGI-middleware кладёт пользователя из Bearer-токена в контекстную переменную на время запроса, а gateway пишет по ней строку `llm_usage` на каждый ответ провайдера отдельной сессией, не влияя на сам вызов при сбое записи. Также считает сводку расхода по пользователю и назначению.
- `learningBack/api/routers/usage.py` — Эндпоинт сводки расхода токенов LLM по периоду, доступный только суперпользователю.
- `learningBack/core/llm_cache.py` — Кэш детерминированных ответов LLM в таблице `llm_cache`, ключ которой зависит от модели, инструмента, схемы и промпта — смена любого из них обесценивает кэш. Сбой чтения или записи кэша проглатывается и не прерывает вызов модели, поскольку промах хуже ошибки пользователю.
### Эссе IELTS/TOEFL (клиент) — Мгновенный офлайн-черновой сигнал по эссе, выбор рубрики оценки по типу письма и отправка на проверку с переходом в офлайн-очередь без сети.
- `learningFront/src/features/ielts-writing/index.ts` — Рендерер письменных активностей IELTS/TOEFL и офлайн-грейдер эссе.
### Языковой трек (ядро модуля) — Типы активностей IELTS/TOEFL, выбор рубрики письма по типу эссе и предмету, провижининг стартового набора (демо-эссе, офлайн reading-дрилл) и объяснение неверных вариантов дрилла.
- `learningBack/modules/languages/generators.py` — Демо-выборка Academic Word List (10 слов) и сборка заготовок карточек AWL для стартовой колоды нового языкового пользователя.
- `learningBack/modules/languages/rubrics.py` — Три рубрики-оценщика письма: IELTS Writing Task 2 по band descriptors и TOEFL Independent/Integrated по трёхкритериальной шкале 0–5, с общей JSON-схемой результата оценки.
### API постановки цели (клиент) — Запросы диалога постановки цели: уточнение, пересказ, подтверждение, предпросмотр объёма пути.
- `learningFront/src/shared/api/goal-intake-api.ts` — Запросы к диалогу постановки цели: уточняющие вопросы по свободному вводу, пересказ цели моделью, подтверждение пересказа человеком — граф области не строится, пока цель не подтверждена этим путём. Отдельно — предпросмотр объёма пути (сколько областей и понятий) до построения графа, полный и интуитивный вариант.
### learningBack/api
- `learningBack/api/routers/content.py` — REST-эндпоинты для материалов (PDF/Markdown): список, деталь с фрагментами, импорт файла и удаление. Делегирует разбор core.materials.extract и хранит результат в Material.
### learningBack/core
- `learningBack/core/ai_gateway.py` — Выбирает реализацию AI-gateway: настоящий провайдер, если задан `LLM_API_KEY`, иначе заглушка `MockAIGateway` — так ключи остаются только на backend'е. Также даёт модулям способ узнать, настроен ли реальный провайдер, и найти рубрику по id/версии.
- `learningBack/core/ai_base.py` — Задаёт протокол `AIGateway` (grade/generate/structured), которому должны следовать все реализации, и JSON-схему результата оценки `Grade`, используемую как схема инструмента при tool calling. Содержит общую сборку промпта оценки из рубрики, задания и ответа пользователя.
- `learningBack/core/ai_mock.py` — Детерминированная заглушка AI-gateway для разработки и тестов без реального провайдера: формирует правдоподобную, но фиктивную оценку по объёму ответа. Используется автоматически, если ключ провайдера не задан.
- `learningBack/core/ai_openai.py` — Реализация AI-gateway поверх любого провайдера с OpenAI-совместимым протоколом chat/completions и tool calling — конкретный провайдер задаётся адресом и слагом модели в конфиге, без отдельного кода. Делает запрос живучим к трём типичным сбоям: обрыв канала, нехватка кредита (адаптирует `max_tokens` под объявленный бюджет) и ответ без вызова инструмента — всё в одном цикле повторов.

## Внешние решения
- **RouterAI Jev: модель решений вместо текста** (S-0001, api, 2026-10-07) — Jev — не чат-модель: получает state и questions с заранее известными вариантами и возвращает вероятности/выбор/оценку вместо текста; тарифицируются только входные токены → docs/development/reference/S-0001-routerai-jev-model-resheniy-vmesto-teksta.md
- **RouterAI: плагины (web, file-parser) и мультимодальные входы** (S-0002, api, 2026-10-07) — Плагины web/file-parser включаются массивом plugins без предварительной настройки; мультимодальные входы (изображения, PDF, аудио, видео) идут через /chat/completions типами контента в messages[].content → docs/development/reference/S-0002-routerai-plaginy-web-file-parser-i-multimodalnye.md
- **RouterAI: выбор провайдера, @-синтаксис, список endpoint-ов** (S-0003, api, 2026-10-07) — Объект provider (order/only/ignore/allow_fallbacks/country) и @-синтаксис в строке model управляют маршрутизацией запроса к конкретному провайдеру модели; GET /models/{author}/{model}/endpoints отдаёт список провайдеров с ценами и лимитами → docs/development/reference/S-0003-routerai-vybor-provaydera-sintaksis-spisok-endpo.md
- **RouterAI: параметры генерации (sampling parameters)** (S-0004, api, 2026-10-07) — RouterAI принимает единый набор параметров генерации (temperature, top_p, top_k, penalties, max_tokens, response_format, tools, verbosity и др.) и передаёт провайдер-специфичные как есть → docs/development/reference/S-0004-routerai-parametry-generacii-sampling-parameters.md
- **RouterAI: режимы обработки flex и priority (service tiers)** (S-0005, api, 2026-10-07) — Поле service_tier на уровне запроса меняет цену и скорость без смены модели: flex дешевле и медленнее (строгий, ошибка если недоступен), priority дороже и быстрее (мягко деградирует до default) → docs/development/reference/S-0005-routerai-rezhimy-obrabotki-flex-i-priority-servi.md
