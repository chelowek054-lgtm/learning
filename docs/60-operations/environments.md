# Окружения и хостинг

> **Черновик для решения человека** (T-0030, R-0020). Составлен по тому, что сегодня требует код; цены и условия
> провайдеров не проверялись и не приводятся — их нужно сверить на момент выбора.

## 1. Что требует Praxis от хостинга

| Часть | Что нужно | Откуда это известно |
|---|---|---|
| API | Python-процесс (uvicorn), 1 процесс на старте (кэш модулей в процессе, A-0021); фоновые задачи (профиль навыка, разбор источников) идут потоком или отдельным воркером | `docker-compose.yml`, `core/worker.py` |
| База | PostgreSQL 17 **с расширениями pgvector и Apache AGE** (A-0024, A-0026): векторы понятий и областей, граф знаний в той же базе | `deploy/postgres` |
| Объекты | S3-совместимое хранилище для загруженных материалов (сейчас SeaweedFS) | `S3_ENDPOINT` |
| Модель | Внешний провайдер LLM по ключу (`LLM_BASE_URL`, сейчас RouterAI); сам сервер GPU не нужен | `core/config.py` |
| Размер | Рабочая база 14 МБ при ~110 тестовых учётках; на первые тысячи человек хватает единиц ГБ | замер 2026-10-11 |
| Время ответа | Долгие запросы (сборка графа 8–10 мин) идут в фоне; хостинг не должен убивать долгие запросы раньше, чем 1–2 минуты | `profile_store.py` |

Главное ограничение: **pgvector и Apache AGE** есть не у каждого «управляемого Postgres». Это сужает выбор сильнее, чем всё остальное.

## 2. Окружения

| Окружение | Для чего | Где |
|---|---|---|
| Локальное | Разработка, тесты (`<db>_test`, схема пересоздаётся каждый прогон) | `docker compose up` |
| Staging | Деплой из `main` с миграциями и бэкапами (T-0031), проверки людьми и живые проверки | по выбору хостинга |
| Production | Реальные люди | по выбору хостинга |

Секреты (`LLM_API_KEY`, `JWT_SECRET`, `ADMIN_SESSION_SECRET`, `PUSH_*`) — в переменных окружения хостинга, не в репозитории; образец — `.env.example`.

## 3. Варианты

| Вариант | Плюсы | Минусы для Praxis |
|---|---|---|
| **Свой VPS (docker compose как сейчас)** | Те же образы, что в разработке: pgvector и AGE уже собраны; предсказуемая цена; можно выбрать страну (политика данных, п. 4) | Бэкапы, обновления, мониторинг — на нас; один сервер — одна точка отказа |
| **PaaS для API (Fly.io, Railway) + свой Postgres на VPS** | Деплой из `main` без администрирования API; масштабирование API отдельно | Две площадки, сеть между ними; страна данных зависит от региона PaaS |
| **Управляемый Postgres (Neon, Supabase) + PaaS** | Бэкапы и обновления делает провайдер | **AGE обычно недоступен**; pgvector — часто есть; придётся пересматривать A-0024 (граф в базе) или переносить граф на обычные таблицы |
| **Российский облачный хостинг** | Хранение данных в РФ (если этого требует аудитория); оплата в рублях, как у RouterAI | Проверить поддержку pgvector/AGE и условия трафика |

## 4. Рекомендация

**Свой VPS с docker compose на старте** (staging и production на разных машинах или в разных проектах), бэкапы
`pg_dump` по расписанию на отдельное хранилище, API за обратным прокси с TLS. Причины: единственный вариант без
переделки архитектуры (AGE и pgvector работают как сегодня), стоимость известна заранее, переход на управляемые
сервисы возможен позже, когда будет понятна нагрузка. Условие пересмотра: больше одного сервера API или требование
доступности выше, чем даёт один VPS.

## 6. Что делает сам код при выкладке

- Миграции: `alembic upgrade head` на старте контейнера API (как сейчас).
- Проверка здоровья: `GET /health`.
- Фоновые задачи: при `JOBS_MODE=inline` — потоком в API (прерванные сборки возобновляются при старте, T-0104); при росте нагрузки — `JOBS_MODE=worker` и отдельный процесс `scripts/worker.py`.
