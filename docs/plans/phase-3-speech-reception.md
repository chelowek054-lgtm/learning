# Фаза 3 — Речь и рецепция

**Цель фазы:** закрыть два оставшихся типа навыка из [педагогического обоснования](../README.md#ключевой-педагогический-вывод-обоснование-архитектуры) — **продукцию речи** (Speaking) и **рецепцию** (Listening / Reading). Первые две фазы покрыли письменную продукцию и удержание, Фаза 2 — модель знаний; здесь появляется работа со звуком и экзаменационный формат на время.

**Ключевой сценарий, который должен заработать end-to-end:**
```
Speaking:  задание → запись голоса на устройстве → сеть → STT → скоринг по рубрике
           IELTS Speaking (4 критерия) → разбор + ошибки в SRS
Reception: passage/аудио закэшированы → дрилл на время ОФЛАЙН → мгновенный
           детерминированный результат → при сети разбор «почему дистрактор неверен»
```

---

## Предпосылки и главное отличие фазы

Фазы 0–2 завершены; движок Activity, AI-gateway (OpenRouter/Claude/Mock), FSRS, sync и модель знаний работают.

> ⚠️ **Эту фазу нельзя честно сделать без устройства.** Speaking — это микрофон и воспроизведение звука; ни `expo export`, ни web-сборка их не проверяют. Клиент Фаз 1–2 **ни разу не запускался на устройстве** — этот долг здесь перестаёт быть отложенным и становится входным условием: `P3-WS0` идёт первым.

**Новые внешние зависимости** — впервые нужен не только текстовый LLM:
- **STT** (речь → текст) для Speaking;
- **TTS** (текст → речь) для генерации listening-материалов.

Оба ложатся на существующую абстракцию: у ядра появляются порты рядом с `AIGateway`, реализации выбираются по ключам (инвариант №2 — ключи только на backend).

---

## Решения, которые нужно принять до кода

| Вопрос | Варианты | Влияет на |
|---|---|---|
| **Где STT** | провайдер по API · `faster-whisper` в контейнере · on-device | WS2, приватность, стоимость, офлайн |
| **Где TTS** | провайдер по API · заранее озвученный банк материалов | WS6, размер кэша |
| **Формат аудио** | m4a/aac (компактно) · wav (совместимо со всеми STT) | WS1 |
| **Хранение записей** | удалять сразу после скоринга · хранить N дней для разбора | WS1, политика приватности |

Первые два — открытые архитектурные вопросы с Фазы 0 ([01 §Открытые вопросы](../architecture/01-architecture.md)); фаза их закрывает.

---

## Definition of Done фазы

1. Запись голоса на устройстве, отправка при сети, STT → текст, скоринг по рубрике `ielts_speaking` (Fluency, Lexical Resource, Grammar, Pronunciation) → разбор.
2. Ошибки из речи попадают в SRS тем же error-log, что и ошибки из письма.
3. `reading_drill` и `listening_drill` проходятся **офлайн** на время, результат считается локально и мгновенно.
4. Разбор дистракторов («почему этот вариант неверен») приходит при сети как online-обогащение, а не как условие прохождения.
5. Аудио и passages кэшируются локально; повторный проход не требует сети.
6. Инварианты сохранены: ключи STT/TTS только на backend, ядро доменно-независимо, единый `response`-лог, connectivity — флаг, а не форк.
7. **Всё перечисленное проверено на устройстве**, а не только сборкой.

## Рабочие потоки

```
WS0 Прогон на устройстве  ← входное условие, блокирует остальные
 ├── WS1 Медиа-конвейер (запись, загрузка, кэш аудио)
 │     ├── WS2 STT-порт и реализация
 │     │     └── WS3 Speaking: рубрика, скоринг, разбор
 │     └── WS5 Listening-дриллы
 └── WS4 Reading-дриллы (звука не требуют — можно параллельно)
       └── WS6 Генерация passages и озвучка
```

Порядок: **WS0 → WS1 → (WS2 → WS3) ∥ WS4 → WS5 → WS6**. WS4 не зависит от аудио и может идти сразу после WS0.

## WS0 — Прогон клиента на устройстве

**Итог:** приложение запущено на реальном устройстве, сквозной сценарий Фаз 1–2 пройден руками, найденные расхождения починены. Без этого нет смысла добавлять микрофон.

- [ ] `P3-WS0-01` Запуск на устройстве через Expo Go (SDK 54); проверить старт, SQLite-миграции, регистрацию модулей.
- [ ] `P3-WS0-02` Сквозной прогон Ф1: регистрация → онбординг → эссе офлайн → sync → скоринг → карточки в SRS.
- [ ] `P3-WS0-03` Сквозной прогон Ф2: граф → плейсмент → курс → шаг → ответ → сдвиг границы.
- [ ] `P3-WS0-04` Починка того, что всплывёт; зафиксировать в ROADMAP список расхождений «сборка vs рантайм».

**DoD WS0:** оба сценария пройдены на устройстве; расхождения либо исправлены, либо записаны с причиной.

## WS1 — Медиа-конвейер

**Итог:** приложение умеет записывать голос, отдавать запись наверх и держать аудио локально для офлайн-прослушивания.

- [ ] `P3-WS1-01` Запись на клиенте (`expo-audio`): разрешения, старт/стоп, длительность, воспроизведение своей записи до отправки.
- [ ] `P3-WS1-02` Хранилище записей на устройстве + очистка: запись живёт до успешной отправки, дальше удаляется.
- [ ] `P3-WS1-03` Загрузка аудио на backend (multipart), привязка к `response`; предел размера и длительности.
- [ ] `P3-WS1-04` Кэш аудио-материалов для listening: скачивание при сети, проигрывание без неё.
- [ ] `P3-WS1-05` Решение по хранению записей на сервере (удалять после скоринга / хранить N дней) — записать в `docs/deploy`.

**DoD WS1:** запись создаётся офлайн, уходит при сети, закэшированное аудио играет без сети.

## WS2 — STT: речь в текст

**Итог:** порт распознавания рядом с `AIGateway`, реализация по ключу, детерминированная заглушка без ключа.

- [ ] `P3-WS2-01` Порт `SpeechToText` в `core/` (доменно-нейтральный: аудио + язык → текст + тайминги).
- [ ] `P3-WS2-02` Реализация по выбранному варианту (см. таблицу решений) + `MockSTT`, возвращающий фиксированный текст.
- [ ] `P3-WS2-03` Job `transcribe`: распознавание как отложенная задача (мост offline→online, как скоринг эссе).
- [ ] `P3-WS2-04` Обработка длинной/тихой/пустой записи: понятная ошибка вместо пустого скоринга.

**DoD WS2:** запись → текст с таймингами; без ключа пайплайн работает на заглушке.

---

## WS3 — Speaking: продукция речи

**Итог:** тип Activity `speaking_response` проходится целиком и питает SRS.

- [ ] `P3-WS3-01` Рубрика `ielts_speaking` v1: Fluency & Coherence, Lexical Resource, Grammatical Range, Pronunciation → band; промпт + schema; seed.
- [ ] `P3-WS3-02` Скоринг: текст из STT + тайминги (темп, паузы) → `Grade`; произношение оценивается по признакам STT, а не «на слух» — ограничение зафиксировать честно.
- [ ] `P3-WS3-03` Feature-слайс `features/speaking`: задание → запись → отправка → разбор по 4 критериям.
- [ ] `P3-WS3-04` Error-log: ошибки речи → карточки SRS тем же путём, что ошибки письма.

**DoD WS3:** устный ответ офлайн → при сети распознан и оценён по рубрике → ошибки в колоде.

---

## WS4 — Reading-дриллы

**Итог:** экзаменационный формат на время, полностью офлайн.

- [ ] `P3-WS4-01` Тип `reading_drill`: passage + вопросы, таймер, навигация по вопросам.
- [ ] `P3-WS4-02` Локальная проверка (`LocalGrader`): MCQ детерминированы — результат мгновенный и без сети.
- [ ] `P3-WS4-03` Online-обогащение: разбор «почему дистрактор неверен» приходит job'ом, отсутствие сети не мешает пройти дрилл.
- [ ] `P3-WS4-04` Экран результата: время, доля верных, разбор по вопросам.

**DoD WS4:** дрилл проходится офлайн с мгновенным результатом; разбор догоняет при сети.

---

## WS5 — Listening-дриллы

**Итог:** то же, что WS4, но со звуком; аудио заранее закэшировано.

- [ ] `P3-WS5-01` Тип `listening_drill`: проигрывание закэшированного аудио + MCQ, ограничение на число прослушиваний.
- [ ] `P3-WS5-02` Локальная проверка и результат — как в WS4.
- [ ] `P3-WS5-03` Поведение при отсутствии аудио в кэше: понятное объяснение, а не пустой экран.

**DoD WS5:** дрилл проходится офлайн на закэшированном аудио.

---

## WS6 — Генерация материалов

**Итог:** passages и озвучка появляются без ручного наполнения.

- [ ] `P3-WS6-01` Генерация passage + вопросов с дистракторами через `AIGateway.structured` (схема и промпт — в модуле `languages`).
- [ ] `P3-WS6-02` Порт `TextToSpeech` + реализация; озвучка passage в аудио-материал.
- [ ] `P3-WS6-03` Курирование сгенерированного: как у графа — draft с confidence, подтверждение админом в панели.
- [ ] `P3-WS6-04` Стоимость: кэш по хэшу входа, чтобы одна и та же генерация не оплачивалась дважды.

**DoD WS6:** из темы получается passage с вопросами и озвучкой, лежащий в кэше клиента.

---

## Проверки в конце фазы

- [ ] Speaking: запись офлайн → STT → скоринг по рубрике → ошибки в SRS (**на устройстве**).
- [ ] Reading и Listening проходятся в самолётном режиме; разбор догоняет при сети.
- [ ] Ключи STT/TTS не в клиенте и не в git; аудио-записи удаляются по принятой политике.
- [ ] `shared/engine` не знает про аудио: запись и проигрывание — в features, порт — в `shared/api`.
- [ ] Единый `response`-лог питает FSRS и адаптацию для новых типов так же, как для старых.

## Открытые вопросы Фазы 3

1. **Оценка произношения.** По тексту из STT её честно не поставить: нужны признаки самого сигнала. Либо ограничиваем критерий и говорим об этом прямо, либо ищем провайдера с оценкой произношения.
2. **Приватность голоса.** Голос — биометрия; политика хранения строже, чем для текста эссе. Решить до первой реальной записи.
3. **Стоимость STT/TTS** на регулярном использовании — считать после первых замеров, не заранее.
4. **Число прослушиваний** в listening-дрилле: экзаменационная строгость (один раз) против пользы для обучения.
5. **Языковой домен и граф знаний.** Фаза 2 построила граф на ML; ложится ли он на язык — открытый вопрос [05 §11](../architecture/05-knowledge-model.md#11-открытые-вопросы). Дриллы этой фазы можно делать без графа, но стоит проверить, не мешает ли это связать их с моделью знаний позже.
