# Решение: Суперпроект с сабмодулями; оркестрация в корне, Dockerfile у сервиса

Когда принято: 2026-07-04. Статус: принято.

## Зачем решали

Система состоит из клиента (Expo) и backend (FastAPI) с разными языками, инструментами и циклами релиза. Документация и оркестрация относятся к обоим.

## Что решили

Корневой репозиторий `learning` — **git-суперпроект**. В нём лежат `docs/`, `ROADMAP.md`, `docker-compose.yml`, `.env.example` и `.data/`. Сервисы — сабмодули `learningFront` и `learningBack`, у каждого свой `main` и origin. `Dockerfile` сервиса лежит в его сабмодуле, корневой compose собирает их вместе. Новый сервис — новый блок в compose и свой Dockerfile.

## Отвергнуто и почему

- **Монорепо с workspaces**: за — Один коммит на сквозное изменение; против — Смешение Python- и npm-инструментов (исходный план с `apps/mobile` отвергнут).
- **Отдельные репозитории без суперпроекта**: за — Независимость; против — Документации и оркестрации негде жить.
- **Суперпроект + сабмодули**: за — Документы и оркестрация рядом с обоими сервисами; сервисы независимы; против — Коммитить и пушить нужно три репозитория и поднимать указатели.

## Последствия

Сквозное изменение — это три коммита: по одному в каждом сабмодуле и подъём указателей в суперпроекте (HANDOFF §1). На файлы сабмодулей `docs/` ссылается путями в тексте, а не markdown-ссылками: по ссылке из суперпроекта GitHub не открывает файл внутри сабмодуля.
