# Переход к платформе: по шагам и что в уже заведённом нужно пересмотреть

## Зачем

Перейти к платформе без остановки и без переписывания всего: каждый шаг оставляет систему работающей и проверяемой прогоном. Порядок выбран так, чтобы дорогое решение (изоляция и публикация сторонних модулей) принималось последним, когда границы уже проверены на своих модулях.

## Что считается сделанным

Шаги по порядку, каждый завершён, когда его проверка проходит и поведение для учащегося не изменилось:

1. **Контракт модуля записан и один.** Манифест, жизненный цикл, версия контракта; серверный и клиентский манифесты сведены. Проверка: базовые модули подключаются по нему, лишний или несовместимый отклоняется.
2. **Граф знаний очищен от предметов.** Нет выбора по названию предмета, предметный стартовый контент вынесен; граф отдаёт интерфейс освоенности. Проверка: тот же код обслуживает три предмета разной природы.
3. **Данные пользователя в одном хранилище.** Ответы, освоенность, карточки пишутся через модуль данных; описаны владелец и срок для каждого типа. Проверка: выгрузка и удаление данных человека целиком.
4. **Интервальное повторение и письмо стали модулями запоминания.** Рубрики и типы заданий приходят от модуля, а не из ядра. Проверка: отключение модуля не ломает граф и данные.
5. **Разрешения и журнал доступа.** Модуль видит только объявленное и разрешённое. Проверка: модуль без разрешения получает отказ, доступ записан.
6. **Изоляция.** Модуль исполняется в песочнице, сеть закрыта по умолчанию, ресурсы ограничены. Проверка: «злой» модуль не получает чужих данных и не выходит за ограничения.
7. **Первая простая мини-игра** на готовом контракте, написанная как будто сторонним автором. Проверка: она не требует правки ядра.
8. **Открытие авторам:** сначала приглашённым, затем каталог.

## Что мешает

- Не выяснено, где исполняются модули (шаг 6), и от этого зависят шаги 1 и 5.
- Часть уже заведённых требований и задач закрепляет прежнюю форму: тип повторения в курсе, выбор стартового контента по названию предмета, предметные рубрики письма, речь и чтение как требования к ядру. Подтверждать их до принятия решения о платформе не стоит.
- Неприкосновенный запас — то, что уже сделано и проверено прогоном: реестр модулей на сервере, учёт расхода, повтор задач, синхронизация прогресса. Оно остаётся и переиспользуется.

## Что осталось сделать

Для уже заведённых записей предлагается разобрать три группы:

- Подтверждать как есть то, что не зависит от формы: реестр модулей (R-0002), AI-gateway (R-0004), плейсмент (R-0015), задания из теории узла (R-0005), синхронизация (R-0025), CI и устройство (R-0016, R-0017).
- Сначала уточнить, потом подтверждать: граф знаний (R-0008) и повторение (R-0024), аккаунт (R-0006), политика данных (R-0018), многоустройственность (R-0019): их границы меняет модуль данных пользователя.
- Пересмотреть как модули или пакеты контента: задачи на код (R-0010), письмо Task 1 и TOEFL (R-0012), граф для языка (R-0013), чтение и аудирование (R-0022), речь (R-0023), ML-трек (R-0014), письмо Task 2 (R-0026), импорт материалов (R-0011).

## Не выяснено

- Нужно ли останавливать новые функции на время шагов 1–5 или вести их параллельно.
- Кто пишет контракт и проверяет его на «втором автором»: без внешнего взгляда он закрепит наши допущения.
- Что делать с уже запущенными пользователями при смене устройства данных: нужна ли миграция и как её проверять.
