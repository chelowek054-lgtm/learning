# Выполнено: реестр модулей и независимость ядра от предметов

## Зачем

Оформить задачей работу, которая уже сделана и проверена, чтобы требование R-0002 не висело без задачи: консоль читает это как «подтвердили раньше времени». Это не новая разработка: задача описывает то, что есть в коде, и ссылается на проверки, которые уже прошли.

## Что считается сделанным

- Ядро backend не импортирует предметные модули и не называет их в коде: модули подключаются через реестр по списку из конфигурации (`INSTALLED_MODULES`) и отдают через общий контракт маршруты, рубрики, типы оцениваемых задач, стартовый контент и представления админки. Решение — A-0001.
- Клиентский реестр диспетчеризует по типу задания без ветвлений по модулю, отклоняет повтор модуля и коллизию типов, берёт названия типов из реестра.
- Ядро клиента не содержит предметных слов; цвета объявлены только в одном файле оформления.
- Проверки инвариантов запускаются в CI суперпроекта на каждый push.
- Стартовый контент выдаёт модуль по выбранному предмету, а не ядро при регистрации.

## Что уже есть в коде

Сервер: `core/modules.py` (контракт и реестр), объекты `backend` в пакетах модулей, потребители реестра в `core/app.py`, `core/jobs.py`, `core/admin.py`, `core/routers/auth.py`. Клиент: реестр в `shared/engine/module`, сборка манифестов в слое виджетов. Скрипт `scripts/check-invariants.sh` и workflow суперпроекта. Всё слито в `main` (learningBack PR 1, learningFront PR 1, learning PR 4).

## Чем подтверждается

Проверки V-0001 (реестр модулей и независимость ядра backend), V-0002 (реестр модулей клиента) и V-0003 (инварианты: ядро и оформление без предметного кода) прогнаны 2026-09-30 и прошли. Карта изменения — M-0001.

## Не выяснено

Не выяснено: нужна ли эта же задача для будущего контракта платформенных модулей, или он оформляется отдельной работой (см. решение A-0020 и контракт C-0001).
