# Решение: где и как размещать backend и базу (предложение, ждёт вашего выбора)

## Зачем

Нужно выбрать площадку для первого развёртывания (staging, затем прод): задачи «Staging: деплой из main с миграциями и бэкапами» и «Переход на EAS» упираются в это решение. Сейчас всё работает как набор контейнеров `docker-compose` (Postgres 16, API, по профилю — фоновый воркер), миграции применяются командой запуска API, секреты берутся из окружения, версия API префиксована `/v1`.

## Что должно быть верно для любого варианта

- Миграции применяются до старта API (уже так в команде контейнера); при нескольких экземплярах — один раз, а не из каждого.
- Секреты и ключ модели только из окружения; сервер не стартует с dev-секретами в staging/прод (уже проверяется).
- Бэкапы базы с проверенным восстановлением и сроком хранения, согласованным с политикой данных (черновик `docs/60-operations/data-policy.md`, п. 4).
- Отдельный процесс воркера для долгих задач (режим `JOBS_MODE=worker`).
- Размещение данных в стране, допустимой для аудитории (см. «Не выяснено»).

## Варианты

1. **Один VPS с docker compose** — текущий стек как есть, Caddy/nginx с TLS перед API. Плюсы: ближе всего к тому, что уже работает и проверяется; полный контроль над регионом; воркер и cron для `purge_expired` — те же контейнеры. Минусы: бэкапы, обновления ОС, мониторинг на вас; нет автоматического масштабирования.
2. **PaaS для API и воркера + управляемый Postgres** (Fly.io, Railway и подобные). Плюсы: деплой из `main` из коробки, TLS и перезапуски, воркер как отдельный процесс. Минусы: расписание задач и миграции до старта надо настраивать их средствами; выбор региона и условия по данным зависят от площадки; привязка к платформе.
3. **Управляемая БД отдельно (Supabase/Neon и подобные) + любой вариант хостинга API.** Плюсы: бэкапы и восстановление в точку времени не на вас. Минусы: задержка между API и базой, если они в разных регионах; лишний внешний провайдер, видящий все личные данные (учитывать в политике данных); расширения Postgres (если понадобится векторный поиск, A-0020) должны поддерживаться.

## Рекомендация

Для staging — **вариант 1** (один VPS с compose): он повторяет текущую среду, не требует переписывать запуск и быстро даёт то, чего не хватает для остальных задач (деплой, миграции, бэкап по расписанию, cron для `purge_expired`). Решение о проде отложить до первых реальных пользователей и до выбора региона; граница с PaaS и управляемой БД лежит в конфигурации (`DATABASE_URL` из окружения), так что переезд не потребует правок кода.

## Не выяснено

- Где находится аудитория и какие требования к месту хранения данных действуют (это определяет регион и допустимость внешних провайдеров; провайдер модели уже внешний).
- Нужен ли векторный поиск в той же базе (A-0020 предполагает pgvector): ограничивает выбор управляемой БД.
- Бюджет и кто будет обслуживать сервер.
- Как проверять восстановление из бэкапа и с какой частотой.
