# Offline-first, синхронизация, очередь задач

## Зачем

Сделать так, чтобы всё, что человек *делает*, работало без сети, а всё, что требует LLM, выполнялось при её появлении без потерь и дублей (vision).

## Состояние

частично — push/pull, очередь, повторы и прогресс FSRS работают; нет авто-триггера и since

## Как должно вести себя

1. **Локальная запись.** Ответы на offline-типы, повторения и постановка AI-задач пишутся в SQLite (`LocalStore`). Сеть для этого не нужна.
2. **Очередь.** Feature, которой нужна AI-оценка, пишет `response` и ставит `job {id (UUID клиента), type, inputRef: {responseId, rubricId}}` со статусом `pending`.
3. **Sync** — две фазы:
   - **Push.** Клиент отправляет `activities`, несинхронизированные `responses`, `pending`-jobs и изменённые `srsCards`. Сервер принудительно проставляет `user_id` из токена, делает upsert по `id` (LWW) и возвращает `ackIds`. Клиент помечает подтверждённые ответы `synced`.
   - **Обработка.** Сервер исполняет `pending`-jobs пользователя синхронно в том же запросе (ADR-0014): оценка → `response.grade` → карточки error-log → `job.status='done'`.
   - **Pull.** Клиент забирает активности, ответы, `done`-jobs и карточки. Карточки применяются **только вставкой**: pull не затирает локальный прогресс FSRS.
4. **Триггеры sync:** открытие «Сегодня», отправка ответа на оценку, ручная кнопка в профиле; **цель** — ещё и переход offline → online и возврат приложения из фона.
5. **Сбой задачи.** Постоянная ошибка (нет ответа, рубрики, неизвестный тип) — сразу `failed` с причиной в `result.error`. Временная (сеть, провайдер, модель не вызвала инструмент) возвращает задачу в `pending` с экспоненциальной отсрочкой `retry_after` (`JOB_RETRY_BACKOFF_SECONDS`=60, вдвое за каждую неудачу); после `JOB_MAX_ATTEMPTS`=3 — `failed`. `/sync/push` берёт только созревшие задачи, `/jobs/process` — любые. Pull отдаёт `done` и `failed`: клиент показывает причину.
6. **Конфликты.** Один активный девайс, LWW на уровне записи. `response` иммутабелен, кроме дописывания `grade`.

## Что система обязана обеспечить

- Всё, что учащийся делает в offline-типах, сохраняется на устройстве без сети. Признак: В самолётном режиме ответ пишется в локальный `response`, повторение обновляет `srs_card`. (Сейчас: реализовано; прежний номер — FR-SYNC-01.)
- Синхронизация двухфазная (push, затем pull), per-user и идемпотентная по `id`. Признак: Повторный push тех же записей не создаёт дублей. (Сейчас: реализовано; прежний номер — FR-SYNC-02.)
- AI-задачи ставятся в очередь офлайн и исполняются при сети: `pending → running → done/failed`. Признак: Эссе, написанное офлайн, оценивается после появления сети без действий пользователя, кроме открытия приложения. (Сейчас: реализовано; прежний номер — FR-SYNC-03.)
- Sync запускается сам: при появлении сети, при возврате в приложение и вручную. Признак: Переход offline → online запускает sync без действий пользователя. (Сейчас: частично; прежний номер — FR-SYNC-04.)
- Pull инкрементальный: отдаёт только изменения с прошлого sync. Признак: `GET /sync/pull?since=` возвращает только записи новее `since`. (Сейчас: принято, не начато; прежний номер — FR-SYNC-05.)
- Неудачная задача повторяется с отсрочкой, после лимита помечается `failed` с причиной. Признак: Временный сбой LLM не приводит к `failed` с первой попытки. (Сейчас: реализовано; прежний номер — FR-SYNC-06.)
- Прогресс повторений (FSRS-состояние карточек) синхронизируется на сервер. Признак: После переустановки приложения интервалы восстанавливаются с сервера. (Сейчас: частично; прежний номер — FR-SYNC-08.)

## Что считается сделанным

- Эссе, написанное офлайн, лежит в локальном `response` и `job pending` — проверка: live web (офлайн-режим браузера); сейчас: сделано. (прежний номер AC-03.1)
- Повторный push тех же записей не создаёт дублей — проверка: live; сейчас: сделано. (прежний номер AC-03.2)
- После push с сетью эссе оценено, ошибки стали карточками, pull приносит их на клиент — проверка: live; сейчас: сделано. (прежний номер AC-03.3)
- Pull не затирает локальный прогресс карточки — проверка: test/ревью `sync-service.ts` (insert-only); сейчас: сделано. (прежний номер AC-03.4)
- Прогресс повторений уходит на сервер; после переустановки интервалы восстанавливаются — проверка: test (сервер LWW, клиент `sync-service.test.ts`); live на устройстве; сейчас: частично. (прежний номер AC-03.5)
- Переход offline → online запускает sync сам — проверка: device; сейчас: не сделано. (прежний номер AC-03.6)
- `pull?since=` отдаёт только изменения новее `since` — проверка: test; сейчас: не сделано. (прежний номер AC-03.7)
- Временный сбой LLM не даёт `failed` с первой попытки; после лимита — `failed` с причиной — проверка: test `test_job_retry.py`; сейчас: сделано. (прежний номер AC-03.8)
- `/sync/push` не принимает запись, id которой принадлежит другому пользователю, и не подтверждает её — проверка: test `test_sync.py`; сейчас: сделано. (прежний номер AC-03.10)
- Весь сценарий AC-03.1..3 проходит на устройстве в самолётном режиме — проверка: device; сейчас: не сделано. (прежний номер AC-03.9)

## Что осталось сделать

- `POST /sync/push` + `GET /sync/pull`: per-user, LWW, идемпотентность по `id` (в прежнем плане — P1-WS2-01, Фаза 1; сейчас: частично.)
- Сквозной прогон Ф1 на устройстве: регистрация → онбординг → эссе в самолётном режиме → черновой сигнал → сеть → оценка → карточки → повторение; ML-трек (в прежнем плане — P3-DEV-02, Фаза 3; сейчас: не сделано.)
- Авто-sync: при переходе offline → online (`expo-network`) и при возврате из фона (`AppState`), с защитой от параллельных запусков (в прежнем плане — P3-SYNC-01, Фаза 3; сейчас: не сделано.)
- Push прогресса FSRS: `srs_card.updated_at` на клиенте и сервере (миграция); push изменённых карточек; LWW по `updated_at`; pull применяет более новые (в прежнем плане — P3-SYNC-02, Фаза 3; сейчас: частично.)
- Инкрементальный sync: push только изменённого после прошлого sync; `GET /sync/pull?since=` (в прежнем плане — P3-SYNC-03, Фаза 3; сейчас: не сделано.)
- Job `transcribe` в фоновом воркере: ADR о воркере вместо синхронной обработки на `/sync/push` (ADR-0014), реализация (в прежнем плане — P4-WS2-03, Фаза 4; сейчас: не сделано.)
- Мониторинг: ошибки клиента и backend, алерты на долю `failed`-jobs и расход токенов (в прежнем плане — P6-OPS-08, Фаза 6; сейчас: не сделано.)

## Не выяснено

- Когда синхронная обработка jobs на push перестанет укладываться в таймаут запроса (Speaking, генерация), нужен фоновой воркер. Решение — ADR перед Ф4 (P4-WS2-03).
