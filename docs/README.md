# Praxis — документация

> Кодовое имя **Praxis** (от *practice*): эффективность обучения даёт практика с обратной связью, а не пассивный контент.

Мобильное приложение (iOS/Android) для персонального адаптивного обучения. Первые предметы — **языки** (подготовка к IELTS/TOEFL) и **технологии** (ML/программирование). Любой другой предмет подключается модулем, а не отдельной веткой кода.

Раздел `docs/` — **единственный источник правды** о системе. Проект ведётся по **DocDD** (Documentation-Driven Development): сначала меняется документ, потом код. Код, расходящийся с документом, считается дефектом одного из них, и расхождение чинится явно.

## Правила DocDD

### 1. Цепочка трассировки

Каждый артефакт ссылается на предыдущий, и по любому звену видно, откуда оно взялось и чем проверено.

```
00-product ─► FR/NFR ─► SPEC ─► ADR (если было решение) ─► задача плана ─► код ─► проверка
  зачем        что        как ведёт себя    почему так        когда            где       чем доказано
```

- **Требование** (`FR-<ГРУППА>-<NN>`, `NFR-<NN>`) формулирует *что* и содержит критерий приёмки. О реализации оно ничего не говорит.
- **Спека** (`SPEC-<NN>`) перечисляет покрываемые требования, описывает поведение и контракт и даёт проверяемые критерии приёмки `AC-<NN>.<n>`.
- **Задача плана** (`P<фаза>-<поток>-<NN>`) ссылается на спеку и требования. Задача без спеки допустима только для инфраструктуры и оформляется ссылкой на `NFR`.
- **Статус требования** выводится из статусов задач, а не ставится руками.

Сквозная матрица «требование → спека → задачи → статус»: [`50-plans/traceability.md`](./50-plans/traceability.md).

### 2. Порядок изменений

1. Новая возможность или изменение поведения: **требование → спека → план → код**.
2. Изменение устройства системы: **ADR → `30-architecture/` → спека → план → код**.
3. Найдено расхождение кода и документа. Если прав код, правится документ, а в спеке в «Журнале» появляется запись. Если прав документ, в план заводится задача, которая чинит код.
4. Решение, принятое по ходу работы, сразу оформляется ADR. Если отложить, оно потеряется.

### 3. Статусы

| Артефакт | Статусы |
|---|---|
| Требование | `proposed` → `accepted` → `implemented` · `deferred` · `rejected` |
| Спека | `draft` → `approved` → `implemented` (все AC выполнены) · `partial` (часть AC выполнена, остаток — задачи в плане) · `superseded` |
| ADR | `proposed` → `accepted` · `superseded by ADR-NNNN` · `rejected` |
| Задача | ⚪ `todo` · 🟡 `wip` · 🟢 `done` · 🔴 `blocked` · ⚫ `dropped` |

### 4. Definition of Done (общее для всех задач)

Задача получает статус `done` только при выполнении всех условий:

1. Выполнены критерии приёмки спеки, на которые задача ссылается.
2. Не нарушены [нефункциональные требования и инварианты](./10-requirements/non-functional.md).
3. Есть **доказательство**, и его вид назван честно: *live* (реальный запуск), *test* (автотест), *build* (typecheck и сборка без запуска), *device* (запуск на устройстве). Одно за другое не выдаётся. Клиентская фича закрывается как `done` только после *live* или *device*; одной *build* для этого мало.
4. Документы обновлены в том же изменении: статус задачи в плане, статус спеки, запись в журнале ROADMAP.

- Спека — [`20-specs/_template.md`](./20-specs/_template.md).

- Задача плана — строка таблицы в плане фазы (формат в [`50-plans/README.md`](./50-plans/README.md)).

## Видение в двух абзацах

Не «ещё одна читалка курсов», а **персональный адаптивный тренажёр** с двумя движками эффективности. **Интервальное повторение на FSRS** удерживает факты, слова и понятия. **Практика с AI-оценкой по рубрикам** отвечает за навыки продукции (эссе, речь, код): AI работает как репетитор, оценивает по официальным критериям и точечно исправляет. Движки связаны **error-log**: ошибки из продукции становятся карточками повторения.

Поверх движков лежит **модель знаний** — граф понятий предмета. По нему система проверяет уровень, строит персональный курс до цели и порождает задания из теории узла. Подробнее — в [`00-product/vision.md`](./00-product/vision.md).

## Инварианты (кратко)

Полные формулировки и способы проверки — в [`10-requirements/non-functional.md`](./10-requirements/non-functional.md#инварианты-системы).

1. **Offline-first.** Всё, что человек *делает*, работает без сети.
2. **AI только через backend.** Ключей LLM/STT/TTS в клиенте нет.
3. **Доменно-независимое ядро.** В `shared/engine` и `learningBack/core` нет предметного кода.
4. **Единый event log.** Каждый ответ пишется в `response`; FSRS и адаптация читают только его.
5. **Connectivity — флаг, а не форк.** Приложение одно; доступность без сети — свойство типа Activity.
6. **Рубрики и узлы версионируются.** Оценка помнит версию того, по чему оценивали.
